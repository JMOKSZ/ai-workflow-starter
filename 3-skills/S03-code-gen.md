# S03 — 代码生成 Skill（含 Harness）

> **用途**: 在受控流水线里生成可交付的代码。  
> **前置条件**: 技术文档已通过人工确认。  
> **核心原则**: 不自由发挥，严格按文档执行。

---

## 执行指令

### 0. 前置阅读

先读以下文件（必须按顺序，不能跳过）：
1. `ARCHITECTURE.md` → 架构理解
2. `2-rules/` 下所有文件 → 行为准则
3. `docs/tech/{{功能名}}-技术文档.md` → 要做什么
4. `harness/workflow.md` → 流水线规则

### 1. 拆任务

按技术文档里的任务分解，一个一个做。每做完一个才能做下一个。
每个任务必须：
- **最小化**：一次只改一个模块/一个文件
- **独立验证**：做完能立即测试

### 2. 每个任务的执行流程

```
步骤 A: 读上下文
   → 读涉及文件的当前代码（确认改之前的状态）
   
步骤 B: 写出实现
   → 严格按技术文档里的定义
   → 遵守 2-rules/ 里的所有规范
   
步骤 C: 自查
   → 是否匹配技术文档？
   → 是否遵守规则？
   → 是否有明显的边界遗漏？
   → 写了必要的日志？
   
步骤 D: 更新文档
   → 如果改了接口签名 -> 更新API文档
   → 如果改了数据模型 -> 更新数据模型文档
   
步骤 E: 验证
   → 跑相关的测试 / 编译 / lint
   → 如果发现失败了 -> 修
```

### 3. 约束条件

**必须做到的**：
- 每改一个文件前，先读完它的当前内容
- 新增文件必须说清楚"新文件"及位置
- 删除代码前检查引用

**禁止做的**：
- ❌ 不允许一次改10个文件然后说"改好了"
- ❌ 不允许修改没让你碰的文件
- ❌ 不允许"顺手"重构（哪怕你觉得需要）
- ❌ 不允许写死值（用配置/常量/环境变量）
- ❌ 不允许生成~~示例代码或死代码~~

### 4. 善后

所有任务完成后：

1. 更新 `ARCHITECTURE.md`（如果结构有变化）
2. 生成变更清单：改了哪些文件、各改了什么
3. 标记"需人工复查"的变更点

## ✅ 完成标准

- [ ] 每个子任务独立完成并验证
- [ ] 代码通过编译/lint/已有测试
- [ ] 架构文档已更新
- [ ] 变更清单已生成
