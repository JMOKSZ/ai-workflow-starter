# S04 — Bug 修复 Skill

> **用途**: 结构化地修复Bug，防止AI"瞎改碰运气"。  
> **适用**: 任何Bug报告、测试失败、异常日志。

---

## 执行指令

### 0. 前置阅读

先读以下文件：
1. `ARCHITECTURE.md` → 理解整体结构
2. `2-rules/` 下相关规则

### 1. 复现

**先别急着改！**

列出：
- 复现步骤（如果有）
- 错误信息 / 日志 / 截图描述
- 发生环境（开发/测试/生产）
- 出现频率（必现/偶发）

如果信息不足 → 列出缺少什么信息，不要开始修。

### 2. 定位

列出 **嫌疑文件**（最多5个，按可能性排序）：
```
1. {{最可能的文件}} — {{理由}}
2. {{次可能的文件}} — {{理由}}
...
```

对嫌疑最高的文件：
- 读引起嫌疑的关键函数
- 检查输入参数是否和预期一致
- 检查边界条件是否被处理

### 3. 假设

提出一个明确的假设：
> "我怀疑 bug 的原因是 {{理由}}，因为 {{证据}}。"

### 4. 最小验证

**不要直接修**。先做一个最小改动来验证你的假设：
- 加一行日志输出关键变量的值
- 加一个 assert 检查边界条件
- 跑一次看看输出是否匹配你的预期

### 5. 修复

假设被验证为真后：
- 做最小必要的修改
- 加测试覆盖这个 case
- 写上注释说明为什么这么修

### 6. 影响分析

改动之后，检查：
- 会影响到其他调用方吗？
- 被改的函数还在其他地方被用吗？
- 需要更新测试吗？

### 7. 回归

跑相关的全部测试确认没引入新问题。

---

## ✅ 完成标准

- [ ] Bug 已复现、定位
- [ ] 假设已被验证（或排除了优先嫌疑）
- [ ] 修复已应用
- [ ] 测试已补充
- [ ] 回归测试通过

---

## ⚠️ 注意事项

- **不要跳步骤**：很多人从"好像大概是这里的问题"直接改，越改越糟
- **一次只改一个嫌疑**：不要同时改3个地方然后说"应该修好了"
- 加日志验证的步骤不要省 —— 这是最快找到根因的方式
- 修完了记得删调试日志（除非是有用的监控日志）
