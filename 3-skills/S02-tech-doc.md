# S02 — 技术文档 Skill

> **用途**: 把已确认的需求文档转成技术实现方案。  
> **前置条件**: 需求文档已通过人工确认。  
> **产出**: `docs/tech/{{功能名}}-技术文档.md`  

---

## 执行指令

### 0. 前置阅读

先读以下文件（必须按顺序）：
1. `ARCHITECTURE.md` → 理解整体架构
2. `2-rules/` 下所有文件 → 理解行为准则
3. `docs/requirements/{{功能名}}-需求文档.md` → 理解要做什么

### 1. 技术分析

逐项明确：

| 维度 | 需要产出 |
|------|---------|
| 影响的模块 | 列出所有要改的模块、新增的文件 |
| 数据模型 | 新增/修改的类、结构体、Schema |
| API 设计 | 新增的接口签名、参数、返回值、状态码 |
| 调用链 | 用户请求从入口到返回的完整路径 |
| 兼容性 | 是否向后兼容？不兼容的地方怎么迁移 |
| 风险 | 做这个改动最可能出事的地方 |

### 2. 写技术文档

在 `docs/tech/` 下创建 `{{功能名}}-技术文档.md`，格式：

```markdown
# {{功能名}} — 技术文档

## 1. 涉及模块
| 模块 | 变更类型 | 说明 |
|------|---------|------|
| {{模块A}} | 新增/修改 | {{做什么}} |
| {{模块B}} | 无变更 | {{但需注意}} |

## 2. 数据模型
```python
# 或 TypeScript / Go / Rust…
class {{新类}}:
    {{字段}}: {{类型}}  # 说明
```

## 3. API 接口
### POST /api/{{endpoint}}
- 请求体: `{ {{字段}}: {{类型}} }`
- 响应: `{ {{字段}}: {{类型}} }`
- 错误码: `400`（参数错） `404`（不存在） `500`（服??错）

## 4. 调用链
```
用户请求 → {{模块A}} → {{模块B}} → {{外部依赖}}
          ↓                   ↓
     {{缓存查询}}         {{DB写入}}
```

## 5. 兼容性
- {{是否向后兼容}}
- {{迁移方案（如果需要）}}

## 6. 风险点
- {{最可能出错的地方}}
- {{应对方案}}
```

### 3. 输出任务分解

把实现拆成 **最小可独立完成的子任务**，每个子任务包含：
- 要改的文件列表
- 预期的改动量（新增几行/改几行）
- 可验证的标准（跑什么命令能确认它做对了）

## ⚠️ 注意事项

- **需要我审**：写完后告诉我「技术文档写好了」，我看过再开始写代码
- 不要写实现细节，只写设计
- 不确定的技术方案用 🤔 标注，列出选项即可（不要替我做决定）
- 如果发现需求文档里有遗漏的场景，在旁边标注【补充需求】
